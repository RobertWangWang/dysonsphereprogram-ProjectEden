# 更新日志

## 1.12.6

**修复：反物质产线那四座建筑，料喂进去了、一件产物都没有。**
视界蒸发炉 / 磁分离塔 / 对产生室 / 彭宁阱复合室，四座全中。

### 病因：分频只写了「压」，没写「放」

这四座不是万倍速，靠的是 `tickDivider = 70`——每 70 个 tick 才结算一次。
实现方式是：轮不到的那些 tick 把计时器压成大负数，让原版紧随其后的那次调用结算不了。

问题出在原版 `AssemblerComponent.InternalUpdate` 是**上一次攒、这一次结**的流水线：

```
0101: if (time < timeSpend) goto 0383;   // 结算，用的是上一次调用攒的 time
0383: if (replicating) goto 0555;        // 否则扣料，replicating = true
055D: if (time >= timeSpend) 不再累加
056F: time += power × speedOverride;      // 攒，给下一次调用用
```

「攒满」和「结算」永远落在**相邻两次调用**上。而分频让攒满的下一 tick 必然是压制 tick，
于是刚攒满的那个周期每次都被抹掉——**每一次，无一例外**。

净效果：第一 tick 扣掉一整份料、`replicating` 置真，此后永远结算不了。
离线复现 7000 个 tick：**周期 0 个、扣料 1 份**，和报上来的现象一字不差。

现在轮到它的那一 tick 会**显式放行一个周期**。判据是 `replicating`——原版只在扣料
（含够不够的检查）之后把它置真、在结算时置假，所以它恰好等于「这一份料付过了、
产物还没发出来」。**结构上不可能凭空造物**：顶多把一个已经付过账的周期提前兑现。

离线复现（7000 tick / 分频 70）：**周期 100 个**，正好是 `tick 数 ÷ 分频数`；
8 / 10 / 35 / 60 秒四种配方长度结果相同。

### 增产剂：比例是量出来的，不是推出来的

第一版让放行的那一 tick 直接把增产计时器推到门槛，结果是**每个周期出一份额外产出**。
离线对照原版同配方同喷涂：原版是 **0.25** 份，这样写是 **1.00** 份，四倍。

原因是原版每累加一次 `time` 涨 `speedOverride`、`extraTime` 涨 `extraSpeed`，
而一个周期只花掉 `timeSpend` 的 `time`——所以一个周期该分到的增产进度是
`extraSpeed × timeSpend / speedOverride`。代进原版自己的两个定义，正好是
**每周期 `incTableMilli` 份**，也就是增产剂标称的那个百分比本身。

改后实测 **0.24 对 0.2503**。压制那一侧也跟着改了：增产计时器不再清零，
而是「倒回上一次调用加的那一笔」，进度原样留着——清零的话喷了等于白喷。

### 顺带：这四座的「参考速率」也跟着分频了

分析面板那两栏原先只按周期数夹，不管分频，于是给这四座报的是满速。
这正是 1.12.5 修过的那类「报一个引擎不允许的数」，补齐。
