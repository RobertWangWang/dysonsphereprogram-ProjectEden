# 更新日志

## 1.12.8

**大型采矿机的产量上限，现在和轨道采集器一样了：600,000,000/秒。**

起因是「气态行星采集器有多快，采矿机能不能跟它一致」。查下来两个数差了 **3600 倍**，
而差距的成因不在开采速度上——**开采速度早就顶满了，一点余量都没有**。

原版的产出是一句整除：`件数 = time / period`。每 tick 往 `time` 上累加
`速度 × 采矿倍率 × 矿脉数`，而 `time` 是 32 位整数，所以累加量必须留在 20 亿以内：

```
每 tick 产量 = 累加量 ÷ period ≤ 20 亿 ÷ period
```

分子这个 mod 早就顶满了（「按满级科技工作」做的就是这件事）。日志里的实测数字把话说死了：

```
抽水站产量：period=720000，当前约 166,667/秒；该建筑的理论上限约 178,957/秒——受 time 为 Int32 约束
行星 Delta Delphini II号星 气体采集速率：600000000/秒 / 69495750/秒 / 600000000/秒
```

**只剩 7% 余量**，所以再怎么调速度都动不了。剩下唯一能动的是分母。

现在 `period` **从采集器那个数倒推**。采集器的速率被夹在「一 tick 填满一个储物格」
（`stations.json` 的 `collectorMaxPerTick`，没配就退回 `slotCapacity`），也就是 1000 万/tick；
`period = 20 亿 ÷ 1000 万 = 200`，采矿机于是也落在 1000 万/tick。
**两边不是各填一个凑出来的数，而是共用同一个锚、按构造相等。**
抽水站和原油萃取站跟着各自的 `boostWaterPumps` / `boostOilExtractors` 一起走。

> **这个数在两边都是「产量不再是瓶颈」的意思，不是真的每秒搬六亿件。** 一 tick 就把机内缓存
> 和物流站槽位填满，之后卡在网络取货的速度上——采集器今天就是这样。想退回原版刻度，
> 把 `advancedminer.json` 的 `minerPeriod` 改成 `0`。

### 动之前核对过的三件事

- **`period` 全程只有三处写**——`Import`、`SetEmpty`、`NewMinerComponent`（后者取自
  `PrefabDesc.minerPeriod`）。**没有任何 UI 能写它**，所以运行时可以双向对齐，
  而不是「配置值只是默认值」那一类。
- **它进存档**，而且 `Import` 不从 proto 重新推导，所以已建成的采矿机必须在运行时补齐。
- **另外 13 处读它的全是显示与统计**（参考速率、理论产能、星球/恒星面板、采矿机面板、
  两个采集器面板），`period` 在它们的算式里同样位于分母，所以面板会跟着一起变大——
  那是**对齐**，不是被改坏。

### 物流：配送运输机运载量 5000，两种飞机的基础速度各 ×10

`stations.json` 新增三个旋钮。

**`courierCarries: 5000`** —— 配送运输机（从配送器/综合物流枢纽飞出来、把货送到机甲手上那种）
的单次运载量，原版基础值 **5**。它和 `droneCarries` 是**两种飞机**：后者管的是物流站之间搬货的
行星内物流运输机（配置里一直是 10000），这一项以前根本没人管。
性质相同——存在 `GameHistoryData` 里、由科技累加、进存档——所以同样双向对齐，调低也生效。
`CourierData.itemCount` 是 Int32，5000 没有宽度问题（这一条是查过的，不是想当然）。

**`droneSpeedMultiplier: 10` / `courierSpeedMultiplier: 10`** —— 两架飞机的**基础**速度，各自 ×10（运输机 8 → 80，配送机 10 → 100）。

最终速度 = 基础 × 科技倍率。两架飞机**结构完全一样**，所以代码里是同一个函数——
同一段推理抄两遍，早晚有一份跟不上另一份。两边的写入点都枚举过：

| 基础值 | 谁写 | 科技写哪个 |
|---|---|---|
| `logisticDroneSpeed` | 只有 `SetForNewGame` / `Import` | `logisticDroneSpeedScale`（@0345） |
| `logisticCourierSpeed` | 只有 `SetForNewGame` / `Import` | `logisticCourierSpeedScale`（@0512） |

也就是说**科技从不碰基础值**，所以改基础值和科技不打架。
代价说清楚：**往后每一级速度科技的收益也跟着放大了**，因为它加成的基数变大了。

> **实现上是「原版基础 × 倍率」算绝对值，绝不在现值上乘。** 这个字段进存档
> （`Export` @0345 / `Import` @074F），在现值上乘的话第二局就是 100 倍、第三局 1000 倍，
> 而且一个字都不报。原版基础值（运输机 8 / 配送机 10）是**活取**
> `Configs.freeMode`——`SetForNewGame` 自己就是从那儿取的；写死数字会在游戏更新改了它之后静默失准。

开机汇总行现在把三种运载量和两种实际速度（基础 × 科技）一起打出来，
两条「基础速度改了」的日志**各有各的标志位**——共用一个的话先跑的会把后跑的那行吃掉，
而「另一架改了没有」恰恰是要看的。

### 修复：蓝图复制了几座重叠建筑，粘贴就建几座

报障：「建筑可以堆叠，蓝图框选也框得到，但一粘贴就只建出来一座」。

**蓝图数据是全的，被关掉的是粘贴预览。** `BuildTool_BlueprintPaste.ArrangeOverlapBP`
专门找同一位置的多个预览（判据是 `(a.pos − b.pos).sqrMagnitude < 0.25f`，即 0.5 米），
命中之后**成对**写两个字段，四处形状一致（@0244 / @025F / @037C / @0397）：

```
V_8.bpgpuiModelId = -1;                                 ← 真正拦住建造的是这个
V_8.condition     = EBuildCondition.BlueprintBPOverlap; // 51
```

而 `CreatePrebuilds` 的**第一道闸就是它，排在 condition 检查之前**：

```
0030: if (bp.bpgpuiModelId <= 0) continue;
003B: if (bp.condition != Ok && bp.condition != NotEnoughItem) continue;
```

所以**只清 `condition` 一点用都没有**——已有的「建造条件放行」作弊清的正是 condition，
这就是为什么那个开关开着也照样只建一座。现在两个一起还原。

**还原成什么值是快照来的，不是猜的**：`bpgpuiModelId` 除了 `ArrangeOverlapBP`，
只有 `.ctor` / `ResetAll`（都写 −1）、`Clone`（原样复制）和蓝图复制建预览时会写，
所以正确的原值就是「`ArrangeOverlapBP` 跑之前的那个」——前置拍快照，后置按快照还原。

> **而第三个字段 `coverbp` 必须留着不动，这一条是反直觉的。**
> 「成对写的要成对还原」会让人想把三个字段全清掉，那样反而会坏：
> `CheckBuildConditions` @256D–2584 拿 `coverbp` 当**豁免**——
> `if (a.coverbp == b) goto skip;` 的意思是「这两个是已知的重叠对，互相不判碰撞」。
> 清掉它，刚还原的那个会立刻被重新判成重叠打回去。**它是通行证，不是标记。**

开关跟着「是什么让建筑能堆起来」走：`cheats.json` 的无碰撞，或 `advancedminer.json` 的
`allowMinerOverlap`。两个都没开时不动原版——那时候重叠建筑本来就摆不下去，
放行只会粘出一片建不成的预览。

### 巨型建筑提速：组装类 ×6、其余 ×3

问的是「万倍速的巨型建筑还能不能再快」。量下来结论是：**能，但现有两个旋钮一个都不是杠杆。**

- `assemblerSpeed` 是 1e8，早就比任何配方的 `timeSpend` 高一两个数量级，一次调用必定填满，再高无效。
- `cyclesPerTick` 配的是 60，而**十六座里只有冶铸熔炉一座够得着**。

卡住其余十五座的是**原版自己的产出闸**，写在 `AssemblerComponent.InternalUpdate` @0138–0184，
按 `recipeType` 分三档：冶炼 `已产出 + 每次产量 <= 100`、组装 `已产出 <= 每次产量 × 9`（上限 10）、
其余 `× 19`（上限 20）。现在那两档乘法闸对**巨型建筑**抬到 `cyclesPerTick`：

| 配方类型 | 原来 | 现在 | 提速 |
|---|---:|---:|---:|
| 组装（天工装配厂、锤锻精工厂） | 36,000/分钟 | **216,000/分钟** | **6 倍** |
| 其余全部（化工、精炼、本 mod 新增的全部类型） | 72,000/分钟 | **216,000/分钟** | **3 倍** |
| 冶炼（冶铸熔炉） | 216,000/分钟 | 不变 | —— |

**冶炼那一档故意没动**：它的闸是加法形状，上限 `100 ÷ 每次产量`，单次产量 1 时是 100，
本来就高过 60——它从来不是被闸卡住的，改了没有收益，却要多算一层乘法。

**判定用「速度 ≥ 巨型阈值」**，和 `MegaTick` 认巨型建筑是同一个判据，所以存档里每一台普通装配机
一个字节都不受影响——这很重要，因为这个方法服务着全存档的装配机。

**匹配点是先数后写的。** 全方法里 9 / 19 / 100 一共出现 9 次，按指令形状
（`ldelem.i4 ; ldc ; mul ; ble`）分类正好是 **7 处乘法闸 + 2 处冶炼加法闸 + 0 处其他用途**；
转译器断言 7，对不上**一处都不改**。这份枚举留成了 `tools/check_output_gate.ps1`，
游戏更新之后离线跑一次就能重新确认，不用进游戏。

> **代价是背压，要知道它会挪到哪。** 这道闸同时是产出缓冲的背压——「闸 20」就是产物攒到
> 20 倍单次产量停手。抬到 60 意味着缓冲深三倍，而下游是物流站槽位和取货速度。
> 所以抬开的是「机器算得慢」，接下来先顶上来的会是「货运不走」。

**顺带修好一个一直在报大的诊断**：本星球普查那行原本拿 `cyclesPerTick` 直接乘台数当「等效普通装配机」，
**完全不知道产出闸的存在**，于是报大了 3 到 6 倍。现在逐台按各自配方类型算，
而且读的是**转译器用的同一个函数**，所以诊断和行为不会各说各话。

### 修复：本 mod 的建筑在电力统计里没有自己的分项

电力统计的分项不是按建筑现算的，而是查一张表：

```
ProductionStatistics.RefreshPowerConsumptionDemandsWithFactory @0054–006D
    conDemands[ powerConId2Index[protoId] ] += requiredEnergy
```

而 `ItemProto.InitPowerFacilityIndices` 是这两张表**唯一**的构建者，调用点也只有一处——
`VFPreload/<PreloadThread>d__51::MoveNext` **@08D8**，而 LDBTool 挂的
`InvokeOnLoadWorkEnded` 在**同一个方法的 @0E11**。所以表建好时 LDB 里一个 mod 的 proto 都还没有；
LDBTool 的 post-patch 清单里没有它，CommonAPI 没有，profile 里其他插件也都没有（逐个 DLL 搜过）。
**这是 `InitFluids` / `InitTurretNeeds` / `itemStackCount` 那一族的第四张表。**

**它不崩，只是记错账。** 两张表都是定长 `new int[12000]`，而本 mod 的物品号在 6500 多、落在界内，
于是读到的是数组默认值 **0**——而下标 0 是构建者开头 `Add(0)` 预留的占位行（查不到任何 proto）。
结果是本 mod 每一座耗电/发电建筑的功率全被汇进那一行无名无图标的占位行。

**总量一直是对的**：`totalConDemand` 在查表之外无条件累加，所以总发电/总耗电和曲线都准，
错的只有「按建筑分项」那张列表。

修法和同族前三张一样：在 `PostAddDataAction` 上把原版自己的构建器再跑一遍（它整表重建，幂等）。

> **时机是这件事里唯一需要想的部分，而且不能往后挪。** `ProductionStatistics.Init` @0084/@0089
> 用这两张表的长度给 `genCapacities` / `conDemands` / `genCount` / `conCount` 定容，而它来自
> `GameStatData.Init` / `Import`——**每次开局或读档**，排在 `PostAddDataAction` 之后。
> 挂在这里，表先变长、统计数组随后按新长度分配；挂到 `GameData.Import` 那种更晚的位置，
> 就会拿新下标去写老长度的数组，直接 `IndexOutOfRangeException`。

核对的是**末态**：凡是打了 `isPowerGen` / `isPowerConsumer` 的 proto 都必须映射到非 0 下标
（真实建筑永远从 1 起，0 被占位行占掉了），有一个落在 0 就报名字出来。

### 一处连带修复

原版往传送带吐货的堆叠层数是 `(36000000 / period × 采矿倍率) / 1800 + 1`，`period` 也在分母上。
周期调小之后这个值会算到两万多，而 `Cargo.stack` 加宽后的上限是 **8191**。
所以它从「只抬高」改成了「抬高**并封顶**」——不封的话 Int16 回绕成负数，
就是本仓库记过的「自动集装机吃货、面板显示负数」那一类，而且一个字都不报。

**顺带**：产量上限那行日志原本整局只打一次，于是三种设备（采矿机 / 抽水站 / 原油萃取站）
里只有最先 tick 的那一种留下记录——而「另外两种是多少」恰恰是这次最需要看的数。
改成按建筑种类各报一次。

> ⚠️ **行星放大仍然默认开着**（1.12.1 起），所以**在 1.12.0 或更早版本下存的档，
> 用这一版打开就废了**。要继续用老存档，在 profile 里新建
> `BepInEx\config\ProjectEden\planet.json` 写 `{ "enabled": false }`，重开游戏即可。
