# 更新日志

## 1.10.6

**修掉一个会让游戏崩溃的 bug：拆掉物流站之后的两秒内可能崩在物流线程上。**
玩家报的堆栈是
`ArgumentNullException ... mono_monitor_enter ... DMD<StationComponent::InternalTickLocal>`。
**这是本 mod 自己的 bug，从 1.10.1 起就在**，只是很难撞上。

病根是 1.10.1 的合并刷新把两种「陈旧」混为一谈了：

- **内容陈旧**（某一格改了物品、新放了一座站）—— 晚两秒无害，这正是那条优化要换的东西；
- **存在性陈旧**（站点没了）—— 是**悬空引用**，不是延迟。

实测链路：`RemoveStationComponent` @02D1 调 `Reset()`，而 `Reset` @00BC 把 `storage`
置 null、@0001 把 `id` 置 0，**组件对象仍然留在 `stationPool` 里**（只是进了回收表）。
紧接着 @02F5 它**同步**重建配对表——所以原版永远不会有一条活着的配对点名一个已死的站点。
而 `InternalTickLocal` @07CF 的判空只判**对象**、不判 `storage`：

```
07C1: V_47 = stationPool[pair.supplyId]
07CF: if (V_47 == null) goto 1175;   // 只判对象
07D6: V_26 = V_47.storage            // 回收过的站点，这里是 null
07E4: Monitor.Enter(V_26, ...)       // ArgumentNullException
```

那个判空在原版**是够用的**，因为它依赖 @02F5 的同步重建。我们把那次重建延迟了最多
120 tick，于是拆掉一座物流站之后的两秒里，其它站点的 `localPairs` 仍然点着它。

> **连发派机（1.10.4）不是病因，但它放大了暴露面**：原版一帧只摸一对配对，现在最多摸
> 10 对，撞上陈旧配对的概率高一个量级——所以它出现在堆栈上。同理 InstantDelivery 也是
> 无辜的：崩溃发生在原版方法体内部，说明它的前置放行了。

> **同源还有一个不崩溃的症状，更难发现**：`stationRecycle` 会把同一个下标发给新建的站点，
> 于是那两秒里陈旧配对会指向一个毫不相干的新站点——**货送错地方，一个字不报**。
> 修掉拆除这一条就一并关掉了。

**修法：拆站触发的那次刷新不再延迟**，就在 `RemoveStationComponent` 内部立刻冲刷——
正好是原版的时机。全程序集只有四处调 `RefreshStationTraffic`（读档 / 改槽位 / 放建筑 /
拆站），**只有拆站是存在性变更**，另外三处照旧合并。代价明说：每拆一座物流站付一次全量
重建，索引版实测 6.7 毫秒，而原版本来就要付 81 毫秒——**逐座重建仍然比原版快一个数量级**，
而「放下建筑」那条路（这条优化真正的目标）一点没变。

**综合化学厂现在也能跑精炼（原油精炼厂）的全部配方。** 兼容表从
化学 2 / 电化学 9 / 氧化还原 10 扩成 **2 / 3 / 9 / 10**，速度仍是 10000 倍。
配置在 `megabuildings.json` 那一座的 `acceptsRecipeTypes`。

这一类当初是漏掉的，而漏掉的代价比看上去大：**`石脑油 · 常减压蒸馏` 是石脑油和蜡油
唯一的来源**，偏偏是精炼类，于是整条有机化学链的**入口**被钉在 1 倍速的原版原油精炼厂上——
下游铺得再快也没用。综合化学厂的立项理由本来就是「C1、氮链、有机化学、炼油线
全卡在 1 倍速上」，这次只是把那句话里的「炼油」真的兑现。

原版的等离子精炼 / X 射线裂解 / 重整精炼也一并能在这里跑：**兼容表按配方类型放行，
不按单条配方**，这是同一个开关的必然结果，不是额外决定。

> **改动本身是一个数字，因为那八处闸门早就换成查表了。** `RecipeTypeCompatPatches`
> 把「配方选择器按 `filter != recipe.Type` 过滤」和蓝图那一族的
> `BuildingParameters.recipeType == prefabDesc.assemblerRecipeType` 全换成了一次查表，
> 加一个类型不需要碰代码。三件白送的事也照旧成立：`SetRecipe` 不校验类型；
> `AssemblerComponent.recipeType` 存的是**配方**的类型，所以精炼配方在这台机器上
> 音效动画仍是精炼厂那一套；那个字段虽然进存档，但全仓库没有任何一处拿它和 prefab 对过。

**顺带补上一个一直存在的审计盲区**（`EnergyAudit.AuditMegaVanilla`）。原来的能量审计
只走 `ores.json` 自己的配方表，所以「能量审计通过」那行的真实含义一直是
**「没有 mod 配方凭空造能量」，不是「没有东西凭空造能量」**——而万倍速机器会非常乐意
跑一条原版配方。新增的第二遍走 `LDB.recipes`，挑出**任何巨型建筑能跑的类型**
（每座自己的 `recipeType` 加上 `acceptsRecipeTypes`）里的原版配方，按产出−投入可燃热值排序，
**只报前 5 条**（一屏警告等于没有警告）。

> 它**只报告，不拦截**：原版的平衡不是本 mod 的责任，而真正的杠杆——巨型建筑允许跑哪些类型——
> 是所有者的设计决定，不该由自检替他做。触发它的正是这次改动：
> **一旦放宽巨型建筑能跑什么，放宽的恰好就是这个盲区**，所以改动点要自带检查。

> 已核对的一点：原版**等离子精炼**（原油×2 → 精炼油×2 + 氢×1）**早就能在万倍速下跑**了——
> `recipes.json` 里有一条把它克隆成化学类（2）的配方，而燔石化工厂和综合化学厂都吃类型 2。
> 所以这次加精炼**没有新开那个口子**。其余几条的实际账目以启动日志里那一行为准，
> 不以注释里的数为准。
