# 更新日志

## 1.12.17

### 修复：产物槽满了的巨型建筑会一直白吃原料

玩家报的是「物流站属性存满了产物，巨型建筑还是会继续生产，不会停止」。
那不是错觉，而且比看起来严重：**产物一件不涨，原料却在以每秒约 29 份的速度凭空消失**，
日志里一个字都没有。

病因是原版两句 IL 的配合，加上本 mod 的分频恰好绕开了原版自己的保护。
重读 `AssemblerComponent.InternalUpdate`（不是从注释里抄的）：

```
0102: if (time < timeSpend) goto 0384      ← Hold 把 time 压成负数，走的就是这条
0129: replicating = false                  ← **先**抹掉「在制」标记
0159-02E8: 产出闸，拒绝时 ldc.i4.0 ; ret    ← **再**判闸，既不恢复标记也不扣 time
037E: time -= timeSpend
0384: if (replicating) goto 0555           ← 这里读到的是那个过期的 false
038E: 扣一整份原料
0550: replicating = true
```

**纯原版是自洽的**：闸拒绝时 `time` 没被扣，所以下一次调用照样从 0102 进结算块、
再被拒一次，**永远走不到 0384 那句 `if (replicating)`**——那个过期的 false 没有读者。

而 `MegaThrottle.Hold` 为了压住原版那次调用（前置钩子取消不了它），
把 `time` 写成 `-speedOverride - 1`，那正好就是通往 0384 的那条路。
于是产物槽满的巨型建筑每个压制 tick 都会**为一个产物永远发不出去的周期再扣一次料**。
`globalTickDivider` 默认是 2，所以每座巨型建筑每隔一 tick 就来一次。

离线复现（`tools/sim_throttle.py`，按 IL 逐条建模）：7000 tick 里结算 120 个周期、
扣料 **3500** 次——**白吃 3379 份原料**。修完之后扣料 121 次，也就是
「120 个周期 + 在制的那一份」，白吃 **0**。

**修法是「不插手」，不是「把标记补回去」。** 上一次结算被闸拒绝过的那一 tick，
不压、不放、不补跑周期，让原版自己那一次调用照原样重新被拒——也就是原版在产物
出不去时本来的行为：停着。补写 `replicating = true` 同样能止住扣料，但会让
`MegaThrottle.Release` 继续往 `extraTime` 里推增产进度，而那是个**存档字段**，
离线量到的漂移是 −6.7e11，足够让 `MegaBatchSettle` 把这台建筑永久踢出批量结算
（同一个坑发作过一次：生产设施 14 ms 变 210 ms）。不写字段就没有这一类后果。

判据是**实测末态**而不是复现闸门条件：「`!replicating` 且 `time >= timeSpend`」
只有闸拒绝这一种收尾会留下——缺料留下的是 `time == 0`、刚建好的是 0、
被压住的是约 −1、正常跑着的 `replicating` 恒为 true。
这样原版将来多一道闸也不会让判据失准。

三件配套的事：

* **烧料那两座不受影响。** 氧化还原燃烧厂和巨型聚变发电站的燃料舱**就是**产物的出口，
  所以 `Burn` 照常跑——跳掉它等于把这两座永久锁死。
* **催化反应器不再被误扣活性。** `LooksProductive` 是复现原版判据的那条退路，
  而它自己的注释就写着它看不见「产物槽满」这一种情况，正是这一种。
* **产量一个周期都没少。** 背压区（每 tick 只排得走 1 / 10 / 100 件）离线量下来
  7118 / 70100 / 420000 个周期，修前修后完全一致——闸拒绝那一 tick 不补跑周期，
  是因为放行那一 tick 一次能结算 `基准 × G` 个周期，追得回来。

新增一行事件日志，**按建筑类型各报一次**：

```
巨型建筑产出闸：「冶铸熔炉」的产物出不去（物流槽位和传送带都满了），这一 tick 起停产……
```

没有这一行的话，「产物槽满时真的停了」和「这段代码根本没进 DLL」在日志里长得一模一样。

### 削减矩阵研究站的囤货，并修掉「科研矩阵全跑到最上层」

玩家报的是两件事：研究站屯了太多货，而且**堆叠建造时所有科研矩阵都跑到最上层去了**。
两件都对，而第二件的病因不是容量本身。

`lab.json` 里那几个存量数原先是「往大了填」定的：生产模式进料和产物各**一千万**，
研究模式每种矩阵**25 万**（那正好是 `matrixServed` 这个 Int32 字段物理上能放的最大值）。
现在四个数都按引擎自己的上限推出来：

| 旋钮 | 原值 | 新值 | 怎么定的 |
|---|---:|---:|---|
| `assembleStorage` | 10,000,000 | **600** | 每 tick 恒定 1 份配方（引擎硬上限），单份按最坏 10 个算是 600 个/秒 → **一秒的满速进料** |
| `assembleOutputStorage` | 10,000,000 | **600** | 引力矩阵单次产 2，即 120 个/秒 → **5 秒的产量** |
| `researchStorage` | 250,000 | **100** | 原版 10 个的 10 倍；按 `ItemPoints=4` 反解能覆盖到 `techSpeed ≈ 8998` 的补料间隔 |
| `supplyAssembleBatches` | 2,000 | **120** | 2 秒的满速生产，而补料间隔只有 10 tick，余量 12 倍 |
| `supplyMatrixItems` | 1,000 | **100** | 跟上限取同一个数；高过上限就是个永远填不满的目标 |

消耗率是推出来的，不是估的。`InternalUpdateResearch` @000A 把每 tick 的哈希预算定为
`(int)(research_speed + 2f)`，而 `research_speed` 由 `FactorySystem.GameTickLabResearchMode`
@00B3 传的是 `(float)GameHistoryData.techSpeed`；一次哈希吃掉 `matrixPoints[j]` 个放大单位
（@0208），而 `matrixPoints[j]` 由 `GameHistoryData.Import` @03C0 填成 `TechProto.ItemPoints[k]`。
所以**每种矩阵每秒吃 `ItemPoints × (techSpeed + 2) / 60` 个**。生产模式那一侧更简单：
`GameLogic` 只有 `_lab_produce_parallel`、没有多周期路径（巨型建筑那套 `RunExtraCycles` 不覆盖
研究站），所以恒定 60 份/秒。

**「全跑到最上层」是另一回事，改容量救不回来。** `UpdateOutputToNext` 里发货方写死
「本层只留 2 个」（IL 0141 的 `7200` = 2 × 3600），而停不停**只**由收货方的 `needs` 决定
（IL 0124 那句 `next.needs[0] == 6001` 是唯一的闸）。那十二处 `36000` 是**每 tick 搬多少**，
是速率——CLAUDE.md 早就记着这句话，而我们的转译器偏偏把它们换成了 `researchStorage × 3600`。
**速率追平容量就等于一 tick 搬空**：下层每 tick 把存货一次性全推上去、自己永远停在 2 个，
于是上层填满之前整座塔的货都在最顶上。25 万对 2 是 12.5 万倍的落差，而原版 10 对 2 只有 5 倍，
所以这个洞在原版参数下根本看不出来。

现在速率拆成了独立的 `researchTransferRate`，**默认 0 = 保持原版的 10 个/tick**（600 个/秒，
已是最苛刻消耗的几十倍）。转译器照样跑、照样断言那十二处——只是写回同一个常量，
这样游戏更新挪了位置会当场报出来而不是静默失准。填了非 0 值又不小于容量的话会被拒回原版并警告。

顺带订正一处单位错误：`supplyIntervalTicks` 的注释原先写「生产模式满速时每 tick 吃 60 份配方」，
实际是 60 份/**秒**、每 tick **一**份，差了 60 倍——而 `supplyAssembleBatches` 的 2000 就是照
那个错数定的。

### 检查器

* `tools/sim_labstock.py`（新增）把上面那些消耗率算出来，反过来问每个候选上限够撑几秒，
  并对 `lab.json` 的实际取值下断言。判据**以原版为锚**而不是以我扫出来的极端值为锚
  （原版 10 个，而原版玩家从不因此饿死）。它还带一组**反向对照**：把 1.12.16 的那套数代进
  同样的判据，逐条确认会被拒——一个从不失败的检查器和没有检查器是一回事。
* `MatrixSurvey` 多报一行研究模式的**实测**消耗：`techSpeed`、当前在研科技的 `ItemPoints`、
  折算出的件/秒，以及现在的上限够撑几秒；撑不过两个补料间隔就 WARN。
  这两个输入一个在 `resources.assets`、一个在存档里，离线读不到，所以 `lab.json` 的推导
  必须由这一行每局核对，否则那段注释就是一句无人核对的主张。
* `tools/sim_throttle.py` 长出了产出闸和物流站槽位这两个闸，能按需复现上面那个原料黑洞。
  **先改检查器再改 C#**——这一版就是靠它发现「把标记补回去」那个修法会让 `extraTime` 漂的。
* `tools/check_output_gate.ps1` 多了六个偏移的定位与前后顺序断言
  （结算入口 / `replicating = false` / 首个闸门 / `time -= timeSpend` /
  `if (replicating)` / `replicating = true`）。游戏更新把其中任何一处挪了位置，
  它会当场失败，而不是让判据静默失准。实测这一版：0102 / 0129 / 0159 / 037E / 0384 / 0550。
