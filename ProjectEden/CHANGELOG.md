# 更新日志

## 1.12.9

**大工厂的逻辑帧从 213 ms 降到 11.5 ms（30 倍），放一座建筑的开销从 60 ms 降到 1.14 ms
（50 倍），产能一件不差。** 外加两处显示修正。

### 巨型建筑的批量结算曾经整局失效，而它一个字都不报

一台喂饱的巨型建筑本该每 tick 只真调一次原版结算，然后把剩下的周期一次性乘上去。
实测它在**每台每 tick 真调 47 次**——批量结算的覆盖率是 **0%**。

根因是一个**存档里的残值**：`MegaThrottle.RewindExtra` 在没喷增产剂时
（`extraSpeed == 0`）往 `extraTime` 写了个 `−1`。而 `extraTime` 是存档字段，
**原版推进它的唯一一处乘的正是 `extraSpeed`**，所以那个 `−1` 永远清不掉；
批量结算当时有一条「`extraTime != 0` 就退回」，于是整个存档的批量结算被**永久关闭**。

> **产量一件不差，只是慢十一倍。** 除了帧时间，没有任何地方报错——
> 这正是最难查的那种故障。

三处修好：那条守卫改成问「计时器会不会动」而不是「它现在是几」
（`extraSpeed == 0` 时计时器被冻住，跨不过门槛，值是多少都无关），
`RewindExtra` 和 `MegaLightPatches.Suppress` 不再往存档字段里塞无用的哨兵。
**守卫那一处的修法是追溯的——已经中招的存档打开就自动恢复，不需要重建任何东西。**

### 巨型建筑全局分频（`globalTickDivider`，默认 2）

单次结算的成本随「这颗星球有多少台」超线性增长，所以真正的杠杆是
**每帧摸到多少台**，而不是每台跑多快。新开关让每座建筑每 G 个 tick 才轮到一次、
轮到时跑 G 倍周期——**吞吐与 G 无关**（周期和分频同乘 G，约掉了），
离线回放验过 G = 1/2/3/4/8 一律 420,000 个周期。

代价是延迟：G = 2 时一台最长等 33 ms 才动一次、单次产出翻倍。对生产线没影响
（下游是缓冲区），对盯着面板看数字跳有影响。想关掉写 `1`，想更激进写 `4`
（7 ms，但单台要等 67 ms）。

实测（同一存档，一颗 9,326 台巨型建筑的星球）：

```
逻辑帧            213 ms → 18.5 ms → 11.5 ms      （修残值 → 开分频）
批量结算覆盖率      0%  →  97.5%  →  98.7%
每台每 tick 真调   47.1 次 →  1.9 次 →  0.8 次
```

### 放一座建筑不再重算整张物流配对表（60 → 1.14 毫秒）

每放一座建筑，原版都要把整颗星球的供需配对表重算一遍。而本 mod 让**每座巨型建筑
同时是物流站**，于是一颗成熟星球有 **8,467 个站、304 万条配对**，一次重算 40~60 毫秒——
连续建造时每两秒顿一下。

改成**增量维护**：一次只重算变更的那几座站点。

```
原版 O(站点²)      81 毫秒
全量索引版         32 ~ 49 毫秒
增量维护           1.14 毫秒      ← 现在
```

> **为什么不能靠换数据结构解决。** 配对表是按物品的等值连接，而这类查询的全量求值
> 下界是 **Ω(输入 + 输出)**（Yannakakis 1981）——输出就是那 304 万条配对，
> **任何数据结构都不可能比「写出自己的输出」更快**。索引早就贴着这个下界了，
> 唯一的出路是别每次都把输出重写一遍。

正确性靠**对账**：每颗星球每 200 次增量插一次全量重建，按多重集比对；对不上就只关掉
增量、保留全量索引版（那仍比原版快一个数量级），而且留下的是全量算出来的表，物流不受影响。
离线还有 `tools/sim_pairindex.py`：逐个加站、随机改槽位、随机拆站、成批变更，
外加两个**负面对照**（故意复现「漏掉小站号对侧」和「批内重复发射」，断言检查器抓得到）。

### 放一座建筑卡 1.3 秒：自检的节流按次数定，而它的代价按规模涨

配对表的回放自检要再跑一遍**原版**的匹配，而那是 O(站点²)。节流写的是「每颗星球头 3 次
+ 每 20 次」，是在一颗 **2,101 站**的星球上定的（当时 81 毫秒）。同一条规则放到 **8,465 站**
的星球上就是 `(8465/2101)² × 81 ≈ 1,300 毫秒`——**每 20 次放建筑冻一秒三，刚进星球时连冻三次**。

改成按**估算代价**节流，阈值从那个实测点反推（81 毫秒 ↔ 2,101² 次迭代 → 压进 30 毫秒
就是约 1,280 站）。大星球跳过并**大声报出估算毫秒数**——静默降级的安全网等于没有安全网；
小星球照常逐条验证，那验的是算法的性质，和星球多大无关。

### 蓝图粘贴：跳过作弊开关反正要擦掉的那些检查

开着「无条件建造」时，`CheckBuildConditions` 里 **6 个「预览对预览」的邻距循环**
和 **1 个「预览对全星球物流站」的邻距块**一次都不进。

逐条枚举过那些区间里的**每一条写入指令**：只写 `BuildPreview.condition`，
一个例外都没有——而那个字段随后就被作弊开关擦掉了。三个离线检查器留在
`tools/`（`check_bp_nest` / `check_bp_inner` / `check_bp_writes`），游戏更新后重跑即可。

> **这不是「粘贴大蓝图卡死」的解药**，只是把可证明作废的工作停掉。在同一个点叠放
> 数千座建筑时仍然会卡——那条路查到 O(预览²) 就没再往下挖。
> 代价：蓝图错误面板不再列出邻距类的拒绝理由（纯显示项，而且那些本来就会被放行）。

### 三处「同一个数的手抄件」

产出闸那个系数在四个地方各存了一份，而 1.12.8 只改了其中两处。
`MegaBatchSettle.BatchSize`（批量只敢批到 20 个周期，剩下的全退回逐次）和
`MegaStationPatches` 的进料备货（备 200 份却要跑 240 个周期，批量被原料卡住）
现在都改成**派生**，不再抄。两处都属于「不报错，只是悄悄慢几十倍」。

> 诊断也跟着改了：`CanBatch` 和 `IsSteadyUnit` 原本各用**一个**计数器汇总
> 四条 / 六条完全不同的退回理由，于是日志只能说「全退回了」而说不出为什么。
> 现在各记各的——**一个分不出分支的计数器量不出东西**，这一招在这一版里连中两次。

### 参考速率 / 理论产能对巨型建筑少报了 3 到 6 倍

1.12.8 把巨型建筑的产出闸从 装配 10 / 其余 20 抬到了 60，而
`ReferenceRatePatches.OutputGate` 里**另有一份写死的 10 / 20**。于是那两块面板
从原来的「多报」直接翻到了「**少报**」——一座天工装配厂实跑 216,000/分钟，面板说 36,000。

日志里两行紧挨着就把它暴露了：

```
参考速率：…组装类到 36,000/min、其余到 72,000/min     ← 旧闸
巨型建筑产出闸：…现在巨型建筑一律放到 60              ← 新闸
```

现在这一处也走 `MegaOutputGatePatches.Scale`，和转译器、本星球普查读同一个函数——
转译器怎么抬，两块面板就怎么跟，构造上不会再分叉。状态行里那几个数也改成现算的。

> **教训记进 CLAUDE.md 了。** 1.12.8 同时改了普查和转译器，让普查读了真函数，
> 却没问「这个常量还有谁存着一份」。**「我让诊断读真函数了」只对你当时看的那个诊断成立**，
> 而这次一次 grep 就能搜出两处。

### 配送运输机的原版基础速度是 6，不是文档里写的 10

`ModeConfig..ctor` 里确实写着 `logisticCourierSpeed = 10`，但 `Configs.freeMode`
把它覆盖成了 **6**——**构造函数里的字面量是默认值，不是这个模式的实际值**。
运输机恰好两边都是 8，所以这个错很容易一直留着。

**代码一直是对的**（它活取 `Configs.freeMode`，正是 `SetForNewGame` 自己读的那个），
错的只有配置注释和更新日志里引用的数字。实测值已经写回去了：

```
运输机基础速度：8 → 80              配送运输机基础速度：6 → 60
运输机运载量由 200 调整为 10000      配送运输机运载量由 20 调整为 5000
```

顺带把配送机运载量的说明改成实测的 **20**（`ModeConfig` 默认 5，科技升上去是 20）——
那正是报障里「运力只有 20」的那个数。
