## `10632ce0`：前向复制与游标更新

入口栈参数依次为未使用参数、源游标地址、源结束地址、目标游标地址、目标结束地址。读取两个游标后，比较两段剩余长度；目标空间不足时，将源结束点截到目标容量，再检查截断点前一字节，若其 `byte & 0xc0 == 0x80`，继续向前退。

之后逐字节向前复制，更新两个游标；EAX 是更新后的源游标。它不是 `memmove`，重叠缓冲区遵循逐字节前向读写的结果。这里也没有完整编码合法性检查：

| 源字节 | 目标容量 | 复制结果 |
| --- | ---: | --- |
| `e2 82 ac` | 1 | `e2` |
| `e2 82 ac` | 2 | `e2` |
| `e2 82 ac` | 3 | `e2 82 ac` |
| 八个 `80` | 5 | 不复制 |

这些是原始指令实测结果。不能将该回退逻辑解释成“保证完整 UTF-8 字符”。调用者是否另有保证仍待查。

## 原始辅助函数联调：消除同步和清零路径的模型假设

`104c30c0` 共 73 字节、31 条指令。其实际行为是：对象非空、对象 `+0xc` 非零且状态指针存在时，比较源记录与工作记录的数据指针。若不同，调用 `105f9bf0` 将工作记录长度指定的字节移到源缓冲区，然后把该长度写回源记录，并把工作记录数据指针改回源缓冲区。返回值始终为 0。

两记录数据指针相同时，长度不会被同步。因此不能把该函数替换为“总是同步长度”，更不能替换为空操作。命令 `0x73` 在这段真实代码返回后，向参数地址写入工作记录指针，并返回 1；参数地址为空时不调用同步函数。

新增测试直接执行原始同步函数、原始内存移动函数 `105f9bf0` 及原始 `memset` `105fb540`，**没有外部函数桩**：

| 完整命令 `0x73` | 12,484 | 同步函数及真实内存移动调用、输出记录指针、空参数分支 |

| --- | ---: | --- |

| `104f52d0` | 28 | 数据非空时先走对应清零释放函数，然后释放记录本身；记录为空时直接返回 |
| `104c6090` | 28 | 指针非空且长度非零时清零，然后选择自定义或默认释放；长度为零仍释放 |

| `10001360` | 26 | 按字节补齐对齐，再按四字节清零及处理尾部；零长度不写入 |

对象清理只有在对象非空、`+0x10` 非零、`+0xc` 非零且 `+0x20` 状态非空时发生。对象为空返回 0，其他情况返回 1。对象标志 `0x200` 会先把源记录的数据指针写成零，从而跳过数据清零/释放，但源记录仍被释放。对象标志 `0x400` 单独存在不会执行这个跳过操作。

源记录 `+0xc` 的 bit 0 选择两条清零释放分支：文件元数据均为 `10b781e0`，行号分别是 `0x32`、`0x34`；记录自身释放使用行号 `0x36`。第二参数非零时，随后再释放工作记录和状态，文件地址 `10b5fb1c`，行号依次为 `0x99`、`0x9a`。最后对象 `+0x20` 被清零。

命令 `0x72` 传入第二参数 0，因此保留工作记录和状态分配；辅助函数返回后，调用者用新参数记录替换源记录，复制新记录到工作记录，并恢复对象状态指针。这一过程已与原始调用者联调，未再用“清理为空操作”的假设。

## CRT 默认释放函数与错误码写回

进一步执行 `10603677` 的真实跳转入口及目标 `10613bf7`，将原来的“默认释放即返回”边界推进到操作系统入口。PE 导入表独立核对 `10b2a434` 为 `KERNEL32.dll!HeapFree`，`10b2a394` 为 `KERNEL32.dll!GetLastError`，未仅依赖反编译器命名。

- 空指针直接返回，不调用系统函数，也不修改 `errno`。
- 非空指针调用 `HeapFree(*(10e823cc), 0, pointer)`；任何非零返回值都视为成功，保留原 `errno`。
- 返回零时，先调用 `10603aac` 获取 `errno` 地址，再读取 `GetLastError`，经过 `10603a33` 映射后写回。
- `10603aac` 调用线程状态提供者 `10617acd`；返回非空时使用状态 `+0x10`，否则使用全局地址 `10e47340`。
- 映射优先扫描原始 `10bbb3c8` 的 45 项键值表，保留首次匹配顺序。未命中时，系统错误码 `19..36` 映射为 13，`188..202` 映射为 8，其他值映射为 22。

## 分配/重分配回调的优先级和默认状态

原二进制 `10e1d018` 初值为 1，随后的三个指针依次为 `104c5f90`、`104c5fe0`、`104c5fc0`，对应分配、重分配、释放包装函数本身。这里确认的是 PE 文件初值；运行时是否被修改和修改接口仍需继续追踪。

`104c5f90` 先检查分配回调：非空且不等于自身时直接尾跳转，保留长度、文件、行号参数。否则长度为零返回 0；长度非零先把 `10e1d018` 写零，再调用默认分配器 `1060d1b8`，将其结果放在 EAX 返回。因此原 Ghidra C 的 `void` 返回推断不准确；现已按证据重新生成带指针返回类型的版本，原始输出仍保留，见下节。

`104c5fe0` 的分派顺序如下：

| 条件（按先后顺序） | 行为 |
| --- | --- |
| 重分配回调非空且不等于自身 | 直接交给自定义回调，传入指针、长度、文件、行号；不在包装层先处理空指针或零长度 |
| 没有上述回调，指针为空 | 走分配逻辑；自定义分配回调仍优先于零长度判断 |
| 指针非空且长度非零 | 将 `10e1d018` 写零，调用默认重分配器 `1060dc5d` |
| 指针非空且长度为零 | 走自定义或默认释放，并返回 0 |

`10e1d018` 的清零发生在调用默认分配器之前，即使默认分配器返回空指针也保持为零。自定义回调、零长度默认请求及释放分支不会由这些包装函数修改该值。当前仅确认读写行为，不将其名称或库外语义当成已证明事实。

`104c61d0` 按顺序把三个回调槽写到非空输出指针；空输出跳过。如果多个输出指针指向同一位置，最后一个非空输出覆盖前面的值。它不修改三个回调槽或 `10e1d018`。

**1,800 组测试**：分配 72 组、重分配 1,296 组、读取接口 432 组。覆盖回调为空/自身/自定义的全部组合、空指针、零和非零长度、`0xffffffff` 长度的参数转发、分配器成功/失败结果、初始状态值、空输出与相同输出地址。实际堆分配和用户回调在边界记录参数并返回给定结果；大长度没有在真实堆上申请。全部 15+54+16=**85 条指令**均执行到；状态清零被改错的负面对照已检出。

脚本 `dsp_native_allocator_dispatch.py`，目录 `allocator-dispatch-behavior/`；保存源初值、原始指令窗口、覆盖与哈希清单。该证据不证明运行时回调设置来源、实际分配器和任意用户回调行为。
