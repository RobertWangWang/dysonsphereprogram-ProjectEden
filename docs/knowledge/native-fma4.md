# Unity FMA4 反汇编补充

## 全局向量初始化值与新发现的导出缺口

已从 CRT 初始化表定位两个原索引未识别的入口，并执行其真实指令：

| 初始化入口 | 表索引（从零开始） | 写入目标 | 四个输出字 |
|---|---:|---|---|
| `180042420` | 259 | `181c82010` | `FFFFFFFF FFFFFFFF FFFFFFFF 00000000` |
| `1800426e0` | 276 | `181c81fb0` | `3EAAAAAB 3EAAAAAB 3EAAAAAB 3EAAAAAB` |

前者从只读地址 `181aeda00` 载入掩码，后者从 `181aeca60` 载入单精度 `1/3` 并复制四份。各自对三种旧内存图案均写入相同结果，输出范围和栈恢复通过核对。因此上一节参数化公式在这两个初始化过程执行之后，按位与得到的权重为 **`(float32(1/3), float32(1/3), float32(1/3), +0)`**。正常有限输入下可理解为前三分量的均值与修正项相加，但仍保留实际逐步乘法/加法舍入；第四分量无穷乘零等特殊情况不能直接删除该运算。

新增 `dsp_native_irradiance_globals.py` 保存初始化代码及结果。比值脚本加入真实初始化配置后，四组配置合计 **3,360 个用例通过**（前三组合成配置保留）。这只证明初始化后的这些值，不排除其他代码随后修改。

进一步将完整 CRT 表与当前函数索引比较，发现 **3,018 个唯一非空回调入口中，2,710 个没有精确对应的 Ghidra 函数入口记录**。这说明此前导出是对“已发现函数”的覆盖，不能据此推定整个模块的全部入口都已发现。缺少精确入口也不等于所有相关字节此前完全缺失，仍需逐项划分函数边界、共享代码和新导出结果。清单保存在 `irradiance-globals/missing-callbacks.txt`，本次两个初始化入口包含在内；下一阶段据此扩展函数发现与反编译范围。

## 阈值前的完整比值计算

已恢复三处比较前的完整 SSE 计算片段：`1813b1686..1813b16e4`、`1813b5a39..1813b5a97`、`1813b9ca6..1813b9d08`（末端不含）。它们具有相同的参数化关系。设输入 XMM8 为 `v[0..3]`，全局向量 `181c82010` 按位与 `181c81fb0` 后作为 `w[0..3]`，缓存旧值为 `old`，XMM4 低位为 `bias`，`R` 表示每步单精度舍入：

```text
p[i] = R(v[i] * w[i])
sum = R(R(p[1] + p[3]) + R(p[0] + p[2]))
denominator = R(sum + bias)
numerator = R(v[3] + (old > 0 ? old : 0))
cache = numerator
ratio = R(numerator / denominator)
```

这里的 `old > 0` 对应 `COMISS` / `JA`；在已测试的屏蔽异常环境中，旧值为 NaN 也取零。缓存写回发生在除法之前，并不以除法产生有限数为条件。后续才进入上一节的 ratio/threshold 比较。保持上述加法分组和逐步舍入，不能用未标明重排的点积替代并声称位级等价。

两个全局向量位于未初始化数据区，不能从磁盘 DLL 中读取并当作运行常量。因此目前保存为显式输入，未擅自赋予颜色权重、归一化系数或误差公式的业务名称。实际启动初始化及上游 XMM8/XMM4 数据来源仍待追踪。

`tools/dsp_native_irradiance_ratio.py` 使用三组可区分按位掩码作用的合成全局配置、十组向量、七种旧值、四种修正项，在三处原始计算片段运行 **2,520 个用例**，缓存值和比值均匹配逐步 binary32 模型。包含正负值、次正规数、大数、无穷、NaN、零分母等样例。MXCSR 固定为 `0x1F80`；NaN 只核对类别，不要求载荷、符号及异常状态位完全一致。

完整片段汇编、输入位模式和输出报告位于 `irradiance-ratio/`。这比仅测试最终比较更进一步，但仍不是实际全局配置、完整辐照度算法、全部浮点语义或端到端运行证明。

## 局部 -1 值的后续阈值用途

继续定位到三个过程中的两级比较：第一处将保存该局部值的 XMM9 / XMM10 与零比较，`COMISS` 后 `JBE` 进入公共分支；正阈值路径另有除法得到的比值，随后 `COMISS ratio,threshold` / `JAE` 也能进入同一分支。

| 函数 | 阈值比较 | 比值比较 | 公共分支 |
|---|---|---|---|
| `1813b1070` | `1813b1674` | `1813b16e4` | `1813b1894` |
| `1813b5460` | `1813b5a24` | `1813b5a97` | `1813b5ca2` |
| `1813b9780` | `1813b9c94` | `1813b9d08` | `1813b9dc1` |

公共分支中均识别到向 `[rcx + rax*4]` 写入 `0xBF800000`（-1.0）的指令。这是另一处缓存槽，不与前文栈上的局部值混为一处。由此可以将先前的局部值暂称为“阈值”，但它的正式业务字段名以及完整重算/复用策略仍未证明。

`tools/dsp_native_irradiance_threshold.py` 执行六个比较片段，共 **396 个用例**通过。MXCSR 为 `0x1F80` 时，第一处对非正值（含 -1、正负零）及不可排序 NaN 都进入公共分支；第二处对有序 `ratio >= threshold` 进入公共分支，比值为 NaN 则不满足 `JAE`。因此不能用不考虑 NaN 的一般比较表达式替代第一处机器码行为。

报告与比较/公共分支汇编保存在 `irradiance-threshold/`。测试直接提供比较时的 XMM 值，未执行中间整段计算，尚未证明入口赋值到所有迭代的完整数据流。比值分子/分母、后续结果复用范围、非默认浮点设置及异常行为仍待核验。

## 哈希后的缓存更新片段

`dsp_native_irradiance_cache.py` 核对三个入口紧随哈希返回的更新逻辑。缓存地址由基址与索引乘四得到；该处保存 32 位哈希，随后四字节保存浮点参数。哈希不一致就写回哈希；另计算任务结构 `+0x2c` 的当前值减缓存值（单精度减法），清除结果符号位，再与 `181aec8b4` 比较。该常量位模式为 `0x34000000`，即 **2^-23**。

只有绝对差**严格大于**该值，才原样写回当前浮点参数。哈希变化或者浮点比较成立，会把局部保存值及对应 XMM 低 32 位改成 `181aed1f0` 的 `0xBF800000`（**-1.0**）；两者都未变化时保留原值。这个局部值的全部后续用途尚未恢复，因此暂不为它命名具体业务字段。

18 种当前值位模式 × 18 种旧值 × 两种哈希关系 × 三处片段，共 **1,944 个原始指令用例通过**。样例包含阈值及邻近可表示值、正负零、次正规数、最大有限值、正负无穷和安静 NaN。比较模型先做单精度舍入；测试在 MXCSR `0x1F80` 下运行，即异常屏蔽、最近舍入、未开启 DAZ/FTZ。在该测试设置中，不可排序的 NaN 差值不满足严格大于条件，所以仅因该比较不会写回浮点缓存；哈希若变化，仍会设置 -1 标志。

整块缓存和输入区同时比较，确认未改动邻接字段；局部值及向量低位一并核对。报告位于 `irradiance-cache/`。这不是完整缓存策略或全运行环境证明；未覆盖未屏蔽异常、信号 NaN、其他舍入模式或函数后续的标志消费逻辑。

## 输入变化检测的整数哈希

三处函数使用 `1813bf290` 汇总输入，再与缓存整数比较。其底层 `1813f10f0` 是 32 位逐字混合函数：初始三状态均为 `(0xDEADBEEF + 4 * word_count + seed) mod 2^32`；每轮消耗三个字，旋转量依次为 4 / 6 / 8 / 16 / 19 / 4；剩余非空尾部进行旋转量 14 / 11 / 25 / 16 / 4 / 14 / 24 的最终混合。无输入时直接返回初始状态。工具使用显式 32 位模运算重写了这个模型，不依赖原 C 的有符号溢出表达式。

`1813bf290` 遍历指针数组，每项只读取四个 32 位字（16 字节），用前一结果作为下一块的 seed。**空指针替换为 `181c32128` 的四个 `0xFFFFFFFF`，不是零块。** 有符号块数小于等于零时返回原 seed。三处辐照度入口传入 `0xFAFAFAFA` 作为起始值；包装器的原 C 漏显示部分调用参数，原始机器码联调确认了 seed 传递。

`tools/dsp_native_irradiance_hash.py` 在 Unicorn 中执行原始整数指令：71 个长度、4 个 seed、3 种字模式，共 852 个底层用例；7 个有符号块数、4 个 seed、3 种空指针模式，共 84 个包装用例，合计 **936 个通过**。包装器调用真实底层哈希指令，只有安全 cookie 检查是返回桩；同时核对栈和非易失通用寄存器，禁止栈外写入。

证据保存在 `irradiance-hash/`，两个辅助入口的查询显示此补充。这里只验证抽样整数行为，不证明无碰撞、完整缓存失效策略或全部光照计算正确，也未据算法相似性声明上游源码身份。

## 零值比较分支与融合运算路径

新增 `dsp_native_fma4_gate_flow.py`，从三个入口开关结束点构建指令级控制流图。直接分支取原机器码，间接分支复用已独立核验的 `normal-flow.json` 目标；其他条件分支均保留两边，调用按正常返回处理。每个函数恰有一处对应局部字节的零值比较；比较到 JE/JNE 之间没有标志覆盖、调用或另一个入口。图检查同时确认所有 FMA4 都必须经过该条件分支。

将该比较每次的结果固定为零后，三个函数的 **120 条 FMA4 全部不可达**；恢复非零边则全部可达，避免因图中漏掉融合指令得到假阴性。证据保存每处比较、条件跳转、零值后继和 40 条融合指令地址，依赖原始反汇编清单哈希。

这是条件化的结构证明：还没有证明入口写入的局部字节在全函数内不会经别名、外部调用或异常路径变化。因此不能据此直接宣称设置环境开关就已得到全输入、全进程的无 FMA4 执行保证。代码与表不变、正常调用返回及既有间接目标范围等前提仍适用。

报告位于 `fma4-gate-flow/report.json`，三个入口查询已增加该结论和限制。浮点运算本身仍为未实现语义的候选，不增加 C 完成数。

## 开关初始化的 CRT 调用链

`180040e90` 的函数指针位于 `.rdata:181891420`，属于区间 `[1818910b0,181896f08)` 的初始化表，槽位索引 110（从零开始）。该表 3,019 项，其中 3,018 项非零。已执行 `181865b2c` 原始遍历指令，记录 CFG 分派点的 RAX 目标；跳过零项后的完整目标顺序与原表一致，栈、RBX 和 RDI 恢复正确。所有回调由返回桩替代，没有运行游戏初始化。

原始 CALL/JMP 和表边界 LEA 支持以下静态链：PE 入口 `1818141c4` → `dllmain_dispatch`（`181814090`）→ 原因分派 `181813ea4` → 初始化过程 `181813ef4` → 表遍历器 `181865b2c`。共四对相邻函数、五处直接边；`dllmain_dispatch` 在不同原因分支有两个调用点，不把它们当成两次必然执行。

保留的调用者 C 和汇编表明：原因值为 1 时进入进程附加初始化；CRT 初始化、启动状态检查、前置初始化表及 C 初始化后置检查成功后，才执行这张表。由此补充下节此前未确定的初始化位置，但没有实际执行 DLL 完整加载、失败回滚或其他线程路径。状态锁和可能的间接写入仍不能仅凭这一条链宣称全部证明。

`tools/dsp_native_fma4_startup.py` 保存五个过程的完整汇编、原 C、表及报告到 `fma4-startup/`。函数连续范围取 PE runtime-function 记录，而非把 Ghidra 的 body 字节总数当连续长度；后者在 `dllmain_dispatch` 中不能覆盖完整尾声。查询已显示启动表证据。

## 全局禁用字节的设置点

发现 `180040e90..180040eaf` 的 31 字节过程：它以 `18189c910` 的原始字符串 `GEO_DISABLE_FMA4` 调用 `181851040`，随后 `test rax,rax` / `setne [181c80780]`。该调用目标的现有反编译符号是 `common_getenv<char>`，函数体加锁后调用无锁环境查询版本。设置点没有解析数字或布尔文本。

因此，该片段的精确行为是 `disabled = (getenv_result != NULL)`。若 getter 返回指向字符串 `"0"` 的指针，禁用值仍为 1；不能把环境值 0 理解为这段代码的“启用”。返回 NULL 则写入 0，覆盖原标志。

新增 `tools/dsp_native_fma4_environment.py` 在 Unicorn 中执行原始设置指令，环境 getter 仅返回受控指针。NULL、`"0"`、`"1"`、`"false"`、合成非空指针指向空串，分别结合先前字节 0 / 1 / 255，共 15 个用例通过；检查查询参数、唯一目标字节写入及栈恢复。**合成空串用例不证明真实 CRT 对空环境变量的返回规则。**

这里只发现并验证该设置点，没有证明它的初始化调用时机、后续是否有其他间接写入或配置线程同步，也没有更改用户环境。证据保存于 `fma4-environment/`，查询入口显示此配置线索。环境变量名称不能单独证明这些函数属于某一厂商库。

## CPU 检测结果与入口开关

`1813f0490..1813f0568` 的 216 字节 CPU 检测过程已完整解码并在 Unicorn 中执行。模拟显式提供 CPUID 返回值，不读取宿主机器能力；安全 cookie 检查使用返回桩，并核对传入的重建 cookie。测试遍历该代码所用的 13 个二值输入（含扩展叶可用性），共 **8,192 种组合**，返回位图、叶查询顺序、RBX 和栈均符合独立位运算模型；全部 helper 指令被执行覆盖。未遍历其余不相关 CPUID 返回位的所有可能值。

| 返回位 | 原始输入条件 |
|---|---|
| 0、1、2 | `CPUID(1).EDX` 的 23、25、26 位 |
| 3、4、5、6 | `CPUID(1).ECX` 的 0、9、19、20 位 |
| 8、10、9 | `CPUID(1).ECX[27]` 为 1，且 ECX 的 28、12、29 位分别为 1 |
| 7（`0x80`） | `CPUID(1).ECX[27]` 为 1，最大扩展叶至少 `0x80000001`，且该叶 ECX 第 16 位为 1 |

三个 FMA4 函数调用该 helper 后，均通过 `test al,al` / `jns` 检查返回值第 7 位，再检查全局字节 `181c80780`。入口局部标志精确等于 `((result & 0x80) != 0) && (global_byte == 0)`，分别写入当前 RSP 的 `+0x70`、`+0x62`、`+0x32`。对每个入口片段遍历 256 种低字节值及全局字节 0 / 1 / 255，共 **2,304 个用例**通过。

该 helper 内没有 `XGETBV`。这是代码范围内的观察，不能推断其他初始化代码没有验证向量状态，也不能推断全局禁用字节永远为零。本次没有执行融合算术，尚未证明局部标志支配全部 FMA4 路径。

复现工具 `tools/dsp_native_fma4_cpu_probe.py` 需要 Capstone 和 Unicorn；`fma4-cpu/` 保存汇编、来源/用例摘要哈希和报告。查询三个入口时显示这一补充。

已从原始机器码确认两个调用者的四条直接 CALL，以及 RIP 相对寻址的任务名字符串。调用者 `1813c1f50` 含 `SolveIrradianceTask` 和方向性辐照度预计算数据缺失的日志；`1813c01c0` 含 `SolveBounceBufferTask`。三处函数的用途标签现有如下依据，但标签不是恢复的原始符号：

|---|---|
| `1813b9780` | 无方向性输出的辐照度求解分支；亦由反弹缓冲任务调用 |

Capstone 对上述代码范围完整解码，无跳过字节。MSVC dumpbin 独立识别全部 120 条四操作数 `vfmaddps`，指令地址、长度与原始字节一致。将 Capstone 给出的指令文本转换为 NASM 的内存操作数语法后，NASM 3.02 重汇编的 **120 条指令逐字节等于游戏机器码**，没有更换乘数、加数或内存操作数位置，也没有把四操作数 FMA4 改写为三操作数 FMA3。

这是指令编码证据，未验证浮点舍入、异常、MXCSR 状态和整个函数的运行行为。后续恢复 C 时应保留融合运算语义，不能仅凭两步乘法与加法生成了看似合理的 C 就认定等价。

## 展开链与代码、数据分离

PE 异常目录中的主入口记录只覆盖 55、55、62 字节；其余片段通过 UNW_FLAG_CHAININFO 链回主记录。工具按链式父记录归组，检查父记录存在、没有循环、各段连续，以及总范围与固定基线一致。三组分别有 7、6、7 个 runtime function 记录。

展开记录的总范围还包含末尾跳转表，因此 **展开范围不能直接当作连续指令范围**：

| 函数 | 四张 RVA 表起点 | 展开范围结束（不含） | 代码与表间填充 |
|---|---|---|---|
| `1813b1070` | `1813b53dc`、`1813b53fc`、`1813b541c`、`1813b543c` | `1813b545c` | 无 |
| `1813b5460` | `1813b96f4`、`1813b9714`、`1813b9734`、`1813b9754` | `1813b9774` | `66 90` 两字节 NOP |
| `1813b9780` | `1813bd53c`、`1813bd55c`、`1813bd57c`、`1813bd59c` | `1813bd5bc` | 无 |

每张表 8 项、每项 4 字节，共 384 字节。各代码范围的直接跳转目标全部落在已解码指令起点；全部 12 处间接跳转都能在附近找到 `cmp eax,7`、无符号 `ja` 和对应 RVA 表访问。表内 96 个目标全部位于所属函数的合法指令边界。报告保存分支上下文与全部映射。

仅上述编码和边界检查未证明范围检查对所有进入路径的支配关系，也未全程验证用于加回 RVA 的寄存器恒为映像基址。后续正常入口分析见下节；异常控制流和外部调用亦未分析完成，不能表述为全函数 C 等价证明。

## 正常入口下的跳转表数据流核验

`dsp_native_fma4_flow.py` 从各函数正常入口开始，对通用寄存器做保守抽象解释。它没有把预期的表目标预先接入控制流：先传播寄存器常量、32 位写入的零扩展范围，以及 `cmp eax,7` / `ja` 的分支约束；只有当表读取的基址确定为 `180000000`、索引确定落在 0..7 时，才读取已固定哈希的 RVA 表，计算跳转目标并继续分析。多条路径汇合取保守并集，扩大中的区间上界保守放宽；未知写入和条件标志清除相关已知事实。

外部调用按正常 Win64 ABI 返回处理：易失通用寄存器与比较标志变为未知，非易失寄存器保留。内存读取通常未知，仅已核验的只读跳转表例外。分析迭代至状态稳定，最后要求所有 12 个间接跳转均被到达并解析，且目标集合与此前记录一致；这不是仅在几组样例输入下模拟。

| 函数 | 保守可达指令 | 已解析间接跳转 | 未解析 |
|---|---:|---:|---:|
| `1813b1070` | 3,742 | 4 | 0 |
| `1813b5460` | 3,762 | 4 | 0 |
| `1813b9780` | 3,435 | 4 | 0 |

“保守可达”允许实际上不可行的分支，不等于每条指令都存在真实输入能执行。第二个函数少的一条是 `1813b5e06` 的 NOP 填充。每张表有 8 个索引、7 个不同目标，其中重复目标没有丢失；报告同时保留原始 96 个索引映射与 84 个按表去重的目标。

两个远距离建立的基址也经过传播核验：`1813b5e5e` 写入 R12，供 `1813b6346` 使用；`1813bbb29` 写入 R11，供 `1813bbfb8` 使用。其余表的基址在附近建立，均在表加载时证明为映像基址。

负例在内存副本中将 12 处范围检查分别从 7 改为 8，对应跳转全部无法继续证明有效；再将上述两个远距离 LEA 的地址各偏移 1，对应跳转也被拒绝，共 **14 个变异检查通过**。未修改游戏文件。

```powershell

python -X utf8 tools/dsp_native_fma4_flow.py
```

每个函数的 `normal-flow.json` 记录代码与分析器哈希、表加载时的基址和索引值、解析目标、不可达指令和负例；文件已加入该函数的 manifest。查询自动校验并展示这份补充。

结论限正常入口、代码与表不被自修改、外部调用遵循正常 Win64 ABI 并返回的条件。未覆盖异常入口、外部直接跳入函数中段、浮点计算语义和调用方功能，尚不构成修复后的 C 输出或整函数等价证明。

## 含不透明融合运算的 C 候选

新增 SLEIGH 扩展 `tools/dsp-fma4.sinc`，覆盖这 120 条已核验的 128 位 `VFMADDPS`。VEX.W=0 和 VEX.W=1 两种编码分别处理第三、第四操作数的位置，不将四操作数运算错误套用为三操作数 FMA。

扩展使用 `DSP_FMA4_PS_RESULT_AND_MXCSR(a,b,c,mxcsr)` 内部操作，其 **20 字节输出只是显式约定的容器**：前 16 字节为向量结果，后 4 字节为更新后的 MXCSR。该内部操作没有实现融合算术，不主张已经验证舍入或异常行为。结果先写临时值，再更新目的寄存器和 MXCSR，避免目的寄存器与输入重叠时提前覆盖输入。上部向量清零沿用 Ghidra 的 VEX 寄存器表示方式。

在独立 Ghidra 12.1.4 副本中加载扩展后，`DspFma4Candidate.java` 对原项目执行只读临时事务：清除选定范围的旧指令、重新解码、逐条核对已有清单的地址/长度/字节、设置完整函数体，最后导出 C 并回滚。三份结果均：

- 覆盖此前的 3,742 / 3,763 / 3,435 条指令。
- 保留 **40 处不透明融合操作**，合计 120 处。
- 不再包含 `bad instruction`、`halt_baddata()` 或跳转表恢复警告。
- 仍保留 security cookie 注入和重叠全局变量警告。

`dsp_native_fma4_candidate.py` 还逐条符号化检查 SLEIGH 生成的 p-code：三个向量输入及其顺序、内存操作数的基址/索引/倍率/偏移、MXCSR 输入、向量与状态输出和上部清零都必须符合上述不透明操作约定。该检查会保留输入寄存器的原值，因此也覆盖输入/目的寄存器别名情形。120 条检查通过；每个函数各有删除上部清零、替换 MXCSR 输入两个负例，共 **6 个变异被拒绝**。

这证明了未知操作前后的数据传递，不证明操作内部融合算术，也不能据此宣称完整函数 C 等价。状态为 **opaque-fma4-candidate-verified**，默认查询继续显示原始结果；只有明确选择候选时才显示这份 C：

```powershell
python -X utf8 tools/dsp_native_query.py 1813b1070 --module UnityPlayer.dll --fma4-candidate --show
python -X utf8 tools/dsp_native_query.py 1813b5460 --module UnityPlayer.dll --fma4-candidate
python -X utf8 tools/dsp_native_query.py 1813b9780 --module UnityPlayer.dll --fma4-candidate
```

每个函数的 `ghidra-candidate/` 保存 C、原始导出报告、120 条 p-code 按函数分组的记录、验证结果与 manifest。三个完整正文查询已检查通过，修改候选 C 副本后查询校验拒绝读取。当前工作使用的 SLA、语言构建输入哈希和 headless 日志另存于 `generated/native/UnityPlayer.dll/fma4-language/`。

### 复现步骤

1. 使用 `tools/build_dsp_fma4_language.ps1 -Ghidra <原版Ghidra目录> -OutputDirectory <独立语言构建目录> -JavaHome <JDK目录>` 构建扩展。脚本复制语言源文件至独立目录，附加扩展并编译，保存输入和输出哈希；没有修改原版语言。已从干净构建目录重建一次，SLA 哈希与实际候选运行使用的一致。
2. 将 Ghidra 复制到一个新的独立目录，以新 SLA 替换副本中 `Ghidra/Processors/x86/data/languages/x86-64.sla`。保留原版用于原始结果查询与对照。
3. 在副本中运行 headless，参数为 `<native/projects> UnityPlayer.dll -process -noanalysis -readOnly -scriptPath <仓库tools> -postScript DspFma4Candidate.java <UnityPlayer.dll/fma4-disassembly>`。本次设置 `JAVA_HOME` 为 JDK，`GHIDRA_HEADLESS_MAXMEM=8G`，每个函数 C 导出上限 120 秒，三项均已结束。
4. 使用安装了 Capstone 的 Python 执行 `tools/dsp_native_fma4_candidate.py --sla <新SLA> --log <headless日志>`，生成独立候选验证标记。只有通过验证的候选才支持上述查询。

扩展只针对这批已核验编码使用，未宣称是完整的通用 FMA4 指令集实现。原游戏文件、原版 Ghidra 语言和保存项目均保持原状。
