# 10632090 扫描函数的完整函数体恢复

本页对应固定 32 位 `rail_api.dll`，SHA-256 为 `c0094678b3cf3a026413f3fcddab3982e3381f1f34ece3473bdb865f8184cad1`。

追踪表 `10632224` 时发现，原补充导出的 `10632090` 函数体只有 **43 字节**，停在 `106320bb` 之前；生成 C 却展开了之后的路径。此前“覆盖核验通过”只证明导出器声明的函数体被完整导出，不能证明声明的函数体范围正确。

现在已在临时 Ghidra 事务中重新解码确定的区间 `10632090..10632222`，恢复两张表的流引用，重新建立函数体并导出 C/汇编，随后回滚。结果为 **403 字节、160 条指令**，新增 C 没有反编译警告；原 43 字节导出保留用于对照。

## 完整性证据

- 独立 Capstone 解码与逐字节检查覆盖整个 403 字节区间，没有空洞、交叠或越界。`10632223` 的 NOP 不纳入函数体；后面为表数据。
- 从入口进行静态控制流遍历，直接分支、返回和两处间接表跳转均有明确边；全部 160 条指令在此图上可达。
- 三处直接调用均指向 `106392d0`。控制流遍历假设该调用返回，不展开其实现，不推断它保留哪些寄存器。
- 两处分派分别测试 `0..255` 与四个 32 位边界位模式，共 **520 组**，执行原始指令并在到达目标块前停止。全部 7 条分派片段指令均执行到；错误字节索引表变异被检出。

## 功能线索与未完成部分

代码对输入指针差的低位作检查，读取成对字节，使用 `param_1+0x4c` 开始的字节分类表或调用 `106392d0`，按分类处理不同长度，并写出推进后的指针。部分分支比较 `]`、`>` 等字符。这里将其称为“扫描函数”是行为描述，不是已恢复的源码符号名或已证明的具体解析器身份。

C 仍包含 `extraout_ECX`、`CONCAT44` 等寄存器/返回类型推断。后续已对 [分类辅助函数](native-scanner-classifier.md) 的全部 65,536 个双字节输入及寄存器效果完成核验，确认它保留 ECX/EDX。扫描 C 的推断错误仍需修正，完整扫描行为和调用方输入布局仍待验证。此次修复不新增函数入口，不改变累计补充入口计数。

## 复现

在原 Ghidra 项目以 `-readOnly -noanalysis` 执行 `DspRepairRailScanner.java`，参数为模块的 `scanner-body-repair` 输出目录。之后在含 Capstone、Unicorn 的环境运行：

```powershell
python -X utf8 tools/dsp_native_scanner_body.py
python -X utf8 tools/dsp_native_query.py 10632090 --module rail_api.dll --show
python -X utf8 tools/dsp_native_query.py 10632250 --module rail_api.dll
```

查询优先展示修复后的 C，并说明验证范围。原始/修复导出分开保存，修复目录含完整汇编、静态边、表映射、模拟统计和哈希清单。
