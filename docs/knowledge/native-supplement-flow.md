# 全批次补充入口的控制转移审计

本轮审计七个模块的重定位补充导出，使用已选择的原函数索引、重试输出及扫描器函数体修复。逐字节再次核对 **15,212 个导出函数体、175,996 条指令**；这里包括三个历史 C 失败标签的汇编，也包括后来识别为数据的候选，不能理解为独立源码函数数量。

## 导出边界检查

除直接 CALL/JMP/条件跳转目标外，还检查每条非终止指令的下一地址是否属于所声明函数体。共发现 326 个顺序后继在导出体外：

| 模块 | 体外顺序后继 | 当时已有精确入口 | 当时没有精确入口 |
| --- | ---: | ---: | ---: |
| rail_api.dll | 302 | 292 | 10 |
| rail_wrapper.dll | 24 | 21 | 3 |

其他五个模块没有此类记录。原有入口存在不等于函数边界一定正确：可能是共享尾部、异常处理块、重叠代码或把内部标签误建成函数。没有入口也不等于代码未导出。所有这些情况保留供归属审查，不自动扩大函数体。

直接边与顺序后继合计指向 **152 个当时没有精确入口的地址**。其中 124 个有原始五字节 E8/E9 证据，已核对源指令和相对目标，再在原 Ghidra 项目只读检查：

| 模块 | 候选 | 新增 C | 已属于原有函数体，跳过 |
| --- | ---: | ---: | ---: |
| rail_api.dll | 121 | 98 | 23 |
| rail_wrapper.dll | 3 | 2 | 1 |
| 合计 | 124 | **100** | 24 |

新增 100 个输出共 **15,886 字节、5,200 条指令**，函数体与原始字节核验通过；15 个输出仍有警告。它们已接入统一查询，模式为 `flow-target-decompiled`。未把候选地址直接等同于独立源码函数，未宣称完整语义恢复。

交叉核对已验证的字节索引表范围，发现此前八个成功生成 C 的候选入口实际位于表数据中：

`10519200`、`105379fc`、`1057d378`、`1057da2c`、`1057ec68`、`105aa8e8`、`105b7bcc`、`1062fc5c`。

### `10630d30`：双字节分类跳过函数

原补充导出仅有开头 8 字节、两条指令。只读临时修复得到区间 `10630d30..10630d77`，共 **72 字节、22 条指令**；原项目更改回滚。`10630d78` 的两个跳转表槽均指向 RET，40 字节索引表仅包含 0 和 1。完整字节、指令边界与静态控制流已经独立核对。

语义为：当前单元高字节为零，且对象 `+0x4c` 分类表中低字节对应分类为 9、10 或 21 时，前进两个字节；否则返回当前指针。Ghidra 初始推断 `void`，现根据 EAX 返回指针证据设置 `byte*`，覆盖记录在报告中。仍保留“所有 switch 分支均到同一目标”的反编译器警告。

**131,200 组原始指令模拟**通过：全部 65,536 个双字节值、低字节与分类值的 65,536 种组合、128 种重复长度。覆盖全部 22 条指令，并检查返回指针、栈平衡、被调用者保存寄存器及零写入。将步长从 2 改成 4 的负面对照被检出。测试要求可读且有停止单元的缓冲区；原函数没有末尾指针检查，有限测试不代表所有输入等价证明。

脚本 `DspRepairRailSkip.java` 和 `dsp_native_skip_body.py`，输出目录 `skip-body-repair/`。统一查询该地址优先返回修复 C：

## 四处 CALL/INT3 的终止路径证据

已进一步追踪调用目标，独立读取二进制并核验跳转：

| 模块 | 历史入口 → 陷阱地址 | 调用链 |
| --- | --- | --- |
| rail_api | `105f97e7 → 105f97ef` | `10602154 → 1060be06` |
| rail_api | `10602180 → 1060218f` | `1060be06` |
| rail_wrapper | `100169fc → 10016a04` | `10019588 → 100195c4` |
| rail_wrapper | `100195b4 → 100195c3` | `100195c4` |

`1060be06` 和 `100195c4` 各有 **67 字节、23 条指令**。局部行为相同：查询信号处理状态，非零时调用 signal 22；标志 bit 1 设置时查询处理器功能 23，非零则令 ECX=7 并执行 `INT 0x29`。其余路径按条件调用报告函数 `(3, 0x40000015, 1)`，随后调用退出入口 `(3)`；即使退出调用返回，下一条也是 `INT3`。局部不存在 RET。

每个模块 **2,304 组测试**，合计 **4,608 组**，遍历全部 256 个标志字节及处理状态/功能结果的 `0`、`1`、`0xffffffff`。每份结果中 768 组到 `INT29`、1,536 组到 `INT3`。逐次核对调用参数和顺序、快失败原因及陷阱处栈值，覆盖全部指令。将 bit 1 检查改成 bit 2 的负面对照被检出。

两个上层入口的普通控制流与对应异常处理块入口，也已静态追踪至唯一 abort 调用。中间的异常过滤器存在单独 RET，但普通入口和已识别异常块入口均不会沿正常跳转到该 RET，不能混成普通返回路径。

**结论仅限局部控制流**：四个历史缺口应视为带陷阱后备的终止转移证据，不应因此扩展到陷阱后的函数。测试把外部处理函数、信号、功能查询、报告和退出调用建模为返回，并在陷阱停止；未模拟操作系统退出、异常处理器继续执行、栈展开或任意回调。没有据此宣称全环境的“不返回”证明，也没有修改原函数的全局 no-return 标记。

工具 `dsp_native_abort_flow.py`；两个模块的 `abort-flow-verification/` 保存原字节、历史缺口依赖、普通/异常入口可达指令列表、分支计数与哈希。查询历史入口、两个上层入口或 abort 地址会显示相应证据。

```powershell
python -X utf8 tools/dsp_native_query.py 1060be06 --module rail_api.dll
python -X utf8 tools/dsp_native_query.py 100195c4 --module rail_wrapper.dll
```

| --- | --- | --- |
| `10416bbe` | `10416bde` | `1041683f` |
| `10416fa9` | `10416fc9` | `10416bfa` |
| `105d3451` | `105d3453` | `105d3413` |

| wrapper `1001b6f8` | `1001b707` | `1001b547`（真实 CALL） |

前八项的来源地址各有一个 `MOV EAX, immediate` 引用，而后续入口还有其他路径跳转进入，构成共享后续代码的证据。前缀可含对象清理调用、状态更新和寄存器恢复；此证据尚未证明异常元数据如何转移到该地址，也未证明唯一的源码函数归属。报告同时保存加载来源地址的关联函数，不能将上述“指向后续入口的函数”直接替代全部归属信息。

### 栈保护失败报告：原始返回路径和系统边界

`dsp_native_security_failure.py` 进一步连接原始 `105d2db8`（251 字节）、`105d2d90`（40 字节）及 `10629b08` 导入跳板（6 字节）。源 DLL 哈希、五个 PE 导入项和异常指针表 `10bb7298 → [10e7bd60, 10e7bdb0]` 均直接核验。

原始控制流如下：

1. 调用 `IsProcessorFeaturePresent(23)`，非零时令 ECX=2，抵达 `INT 29h`。模拟在此停止，不模拟内核异常处理。
2. 零值时保存寄存器、段寄存器和 EFLAGS 到全局上下文；异常码为 `0xC0000409`，异常标志为 1，参数个数为 1，首参数为 2。异常地址和上下文 EIP 来自入口返回地址，记录的 ESP 为入口 ESP+4，EBP 为调用者原值。
3. 调用 `SetUnhandledExceptionFilter(0)`，再调用 `UnhandledExceptionFilter(10bb7298)`，随后调用 `TerminateProcess(GetCurrentProcess(), 0xC0000409)`。前两个 API 的返回值不会改变这条顺序。
4. 如果显式返回模型令 `TerminateProcess` 返回，两个原始函数均执行栈恢复及 `RET`，最外层 EAX 保留模型返回值。DLL 中确有这些指令，不能把 Ghidra 的 `noreturn` 元数据当作不存在返回路径的机器码证明。这不表示真实进程终止会返回。

### malloc 重试与原始 new-handler 查询连接

`dsp_native_malloc_base.py --original-handler` 将原来的 `callnewh` 返回模型替换为原始 `1060ed90` 调用封装，并连接 `1060edd4` 编码指针查询、`1060ee1d` 解锁路径、`105d42c0` / `105d4306` 正常 SEH 帧操作、原始 cookie 检查和初始 RET guard。原始 malloc 核心、重试开关读取及 errno 指针选择也在同一模拟中执行。

验证的连接行为：

- 每次分配失败后重新读取重试开关；关闭时不会查询或调用处理器。
- 开启时查询编码的处理器指针。空指针使重试结束并设置 errno=12；非空指针通过 guard 调用用户回调。查询使用锁 0，调用回调前已解锁且 FS 异常链恢复为原值。
- 原始调用封装把非零回调返回值归一化为 1，允许再尝试分配；回调返回零则失败。回调修改重试开关为零之后，仍先进行下一次分配；只有该次分配也失败，才重新检查开关。
- 超限大小不调用 HeapAlloc；零大小变为 1。最终成功保留 errno，失败由原始 TLS/全局回退路径写入 errno=12。调用者保留寄存器、栈位置、编码处理器槽及 FS 链均核验。
