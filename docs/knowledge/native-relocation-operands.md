# 从重定位操作数找回缺失的表引用

本轮继续审计 32 位 `rail_api.dll` 中此前标记为“无可独立解码引用”的 210 个数据地址。源文件固定为 SHA-256 `c0094678b3cf3a026413f3fcddab3982e3381f1f34ece3473bdb865f8184cad1`。

交叉引用列表为空不能证明没有引用：PE `HIGHLOW` 重定位仍记录了这些地址出现在机器指令中的具体位置。对每个目标找到重定位槽，再在原 Ghidra 项目检查包含该槽的指令，独立验证指令字节、边界、位移位置、位移宽度和实际内存操作数。

## 结果

以下第一批统计保留为历史记录。后续已找回全部 210 项引用，当前总计 188 个字节索引表、22 个绝对跳转表；统一验证现覆盖 208 处分派、9,580 个表内索引和 9,996 组模拟。另两个非紧邻表有专门片段验证。最后十处边界的恢复见下方补充；整个目标函数的语义仍未因此自动得到证明。

| 分类 | 数量 | 本轮证据 |
| --- | ---: | --- |
| 字节索引表 | 188 | `MOVZX reg, byte [index + table]`，紧接使用所加载寄存器的四字节绝对跳转表 |
| 绝对跳转表 | 7 | `JMP [index*4 + table]`，重定位恰好位于 32 位位移字段 |
| 重定位位置尚未解码 | 15 | 原项目该位置没有包含指令，未猜测指令起点或强行认定为表引用 |

已确认的 195 项中，193 张表的紧邻指令是同一索引寄存器的 `CMP reg, bound; JA default`，可据此读取表内映射，共 **9,079 个输入索引槽位**。两项 `10528544`、`10555a10` 不符合这一紧邻模式，后续片段证据见下节；最初批次统计保留。

193 张表逐张执行原始 x86 分派片段：遍历 `0..bound`，再测试 `bound+1` 和 `0xffffffff`，合计 **9,465 组**通过。模拟在到达目标块时停止，不执行被分派的函数体。将一张表的第一个目标改动一个字节地址的负向检查成功检出目标不符。

这里的索引范围是分派片段入口处的寄存器值。例如 `100b77db` 读取 `100b7d10`，紧邻边界为 `0..69`，随后通过 `100b7c84` 的指针表跳转；更前面存在索引变换，因此不能直接把 `0..69` 解释为源语言的原始输入值。

## 仍需继续的部分

### 两处非紧邻边界的后续核验

`10528544` 的索引由 `10526ecf` 的 `CMP EAX,30; JA 10527a0e` 约束；检查与 `10526ee7` 的跳转之间插入了两次 LEA、两次栈写入和一次栈读取，它们不改变 EAX。已恢复 31 项绝对地址映射，验证 68 个索引位模式 × 3 个 ECX 值，共 **204 组**。同时核对整页栈内存与 EDI 状态：表内路径写入 ECX+0x58、ECX+0x5c，并从局部槽恢复 EDI；越界路径不执行这些写入。

`10555a10` 使用的值来自 `105557ca..1055583b` 的标志选择器，写入 `[ESP+0x20]`。其判断优先级及产生值：

| 按顺序命中的标志 | 保存值 | EDI |
| --- | --- | --- |
| `flags & 1` | `0x1001` | `0x12` |
| `flags & 2` | `0x1001` | `0x13` |
| `flags & 0x10` | `0x1001` | `0x16` |
| `flags & 4` | `0x1001` | `0x14` |
| `flags & 0x800` | `0x1002` | `0x1e` |
| `flags & 0x100` | `0x1004` | `0x1c` |
| 均未命中 | `0x1000` | `0x0c` |

后续 `105558d6` 对 EAX 减去 `0x1000`，再在 `105558db` 间接跳转。因此，将选择器产生值传入该片段时，表索引只会是 **0、1、2、4**。遍历全部 4,096 个低 12 位组合，并分别叠加两种高位模式，共 **8,192 组**；核对保存值、EDI、整页栈内存及分派目标。五项原表完整保留，不能因为本选择器不生成 3 就删除该项。

两组验证合计 **8,396 例**，覆盖三个片段的全部 **40 条指令**；错误指针变异被检出。第二组把选择器结果直接送入后续分派，没有执行中间的分配、释放等外部调用，**不证明这些调用不能改写保存值**，因此这是局部值域与分派证据，不是完整入口可达性证明。

证据在 `nonadjacent-table-bounds/`，复现命令为 `python -X utf8 tools/dsp_native_nonadjacent_tables.py`。查询两个表地址会显示对应补充说明。本轮不改原 C 或增加函数数。

### 尚未解码的位置

原来尚未解码的 15 项已完成后续定位：14 项位于此前 `relocation-callbacks` 导出的函数体内；核对该批清单、函数体范围、汇编文件哈希以及实际指令的重定位位移后，恢复引用。原 Ghidra 项目未包含这些临时补建函数，因此不能仅查原 listing 判断它们仍未解码。

最后一项 `10632224` 的引用位于 `106320e5`。已核验补充函数 `10632090` 内 `106320ac` 的 `JE 106320bb`，再从这个明确的分支目标独立解码至 `106320ec`，找到 `CMP EAX,10; JA default; JMP [EAX*4+10632224]`。没有通过任意向前试探来猜测指令起点。分支、49 字节后续解码和出处写入验证报告。

另发现覆盖问题：`10632090` 原导出函数体仅 **43 字节**，但其 C 展开了后续路径。后续已完成 [完整函数体修复](native-scanner-body.md)：403 字节、160 条指令及两张跳转表，520 组分派验证；查询优先展示修复结果，原文件保留。完整扫描语义与外部辅助函数仍待核验，累计补充入口数不变。

已经确认的表也不代表分支目标语义恢复完成；未在本轮证明调用方输入域、全部目标块、原 C 的 case 标签或整个函数等价性。本轮没有增加任何独立函数/C 入口计数。

## 复现与查询

对原 `rail_api.dll` Ghidra 项目，以 `-readOnly -noanalysis` 执行 `DspRelocationOperandAudit.java`，参数为该模块的已选导出目录。脚本只读取原始 listing，不修改项目。随后在安装 Capstone、Unicorn 的 Python 环境执行：

```powershell
python -X utf8 tools/dsp_native_relocation_operands.py
# 数据表地址可直接定位到拥有引用指令的函数
python -X utf8 tools/dsp_native_query.py 100b7d10 --module rail_api.dll --limit 1
```

原始审计、独立核验、全部表映射与依赖哈希位于 `generated/native/DSPGAME_Data__Plugins__x86_64__rail_api.dll/relocation-operand-audit/`。查询工具核验这些证据后显示表引用和边界说明；此前失败审计文件作为历史输入保留。
